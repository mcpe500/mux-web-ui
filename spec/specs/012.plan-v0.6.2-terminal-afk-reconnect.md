Permintaan user (2026-08-25):

> *"ini web nya setelah berapa lama saya buka terus saya AFK kok tiba-tiba terminal-nya offline? padahal codex session ada dan masih running? atau bahkan kalo terminal nya diem gitu kok diem-diem aja?"*

Keputusan developer (2026-08-25): cabut akar penyebab lewat **dua lapisan**. Pertama **client-side**:
`TerminalView` saat ini hanya melakukan attach WebSocket satu kali tanpa auto-reconnect, sehingga begitu
koneksi putus di tab AFK, UI menampilkan overlay permanen "Disconnected". Kedua **server-side**: begitu WS
putus, server memanggil `detach_session` → `has_client=false`, lalu janitor men-reap PTY setelah grace
period (default 60 detik) dan membunuh seluruh process group — termasuk proses codex yang masih hidup.
Spec ini menambahkan auto-reconnect yang aman, perlakuan tab hidden/visible, indicator reconnecting,
serta pengaturan reap yang tidak agresif agar proses pekerjaan tidak mati saat user AFK sejenak.

Dikerjakan TDD mengikuti [`000a.plan-test.md`](./000a.plan-test.md) dan checklist
[`012b.plan-checklist.md`](./012b.plan-checklist.md). **Prinsip**: (1) regresi nol — 161 test cargo +
70 test vitest existing hijau; (2) tetap aman — WS token tetap single-use TTL 10 s, satu socket aktif;
(3) budget aset ≤750 KiB gzip dipertahankan; (4) proses aktif tidak dibunuh tanpa sengaja.

## 1. Latar Belakang

### 1.1 Skenario User

1. **AFK di HP**: user membuka web lalu layar mati / tab ke-background / membiarkan terminal diam dalam
   waktu lama. Setelah kembali, terminal menampilkan "Terminal Disconnected / Exited" padahal proses
   (contoh: codex) masih berjalan di sisi shell.
2. **Tidak ada cara menyambung ulang**: tidak ada tombol buat re-attach; user harus reload penuh atau membuka
   terminal baru (yang mempercepat session lama dibunuh).
3. **Proses lenyap**: karena grace reap server (60 s default), session lama kerap sudah di-reap saat user
   kembali → data PTY & proses hilang.

### 1.2 Kondisi Saat Ini (fakta kode — titik awal)

| Fakta | Lokasi | Implikasi |
|---|---|---|
| WebSocket dibuat satu kali (`fetch /attach` → WS), tanpa logic reconnect | `web/src/apps/terminal/TerminalView.tsx:60-74, 203-211` | WS putus = permanen "Disconnected" |
| `ws.onclose` hanya set overlay, tidak menyambung ulang | `TerminalView.tsx:132-139` | Tidak ada auto-recovery |
| Server kirim ping tiap 20 s; client jawab PONG (opcode 0x05→0x06) | `src/http.rs:1571,1593-1596`; `TerminalView.tsx:114-118` | Keepalive normal saat tab aktif |
| WS `close`/gagal kirim → `detach_session` → `has_client=false` | `src/http.rs:1648-1662` | Antara detach sampai reap, sesi menganggur |
| Reap grace `session_idle_timeout` default **60 s**; busy-grace 30 s hanya menunda selama output mengalir | `src/config.rs:61-68`, `src/session.rs:52-62` | AFK idle ≥60 s → PTY `terminate()` |
| Janitor reap → `remove_session` → `pty.terminate()` (kill process group) | `src/session.rs:293-330, 413-422` | Proses codex berhenti bila tertunda cukup lama |
| Ring buffer + replay tersedia saat re-attach (SESS-007) | `src/session.rs:345`, `src/http.rs:1546-1559` | Reconnect dapat menampilkan riwayat output |
| Reattach token single-use TTL 10 s; gen naik (kicks client lama) | `src/session.rs:338-363` | Setiap reconnect = attach baru yang benar |
| `attach_session` meng-clear idle_deadline & set `has_client=true` | `src/session.rs:382-388` | Reattach otomatis menonaktifkan reap |

### 1.3 Risiko Tanpa Desain

- **Reconnect loop tak terbatas** pada sesi yang sudah hilang → request spam `POST /attach` (rate-limit / log banjir).
- **Overlay tidak sinkron**: reconnect tidak boleh menghidupkan sesi yang sudah `SessionState::Closed`
  atau frame EXIT (opcode 0x03) telah diterima.
- **Reap terlalu cepat** membunuh proses pekerjaan saat tab di-background sebentar.
- **Menaikkan default idle timeout** mengubah perilaku server; harus didokumentasikan dan tetap dapat `=0` (disable reap).

## 3. Milestone

### Milestone A — Auto-reconnect client (AFK-001..004, 007)

`TerminalView.tsx` (file `web/src/apps/terminal/TerminalView.tsx`) diberi logika reconnect:

- Refactor attach menjadi satu fungsi `attach()` yang bisa dipanggil ulang: `fetch POST /attach` → token →
  `new WebSocket` → memasang semua handler (onopen/onmessage/onclose/onerror) yang sama.
- Pada `ws.onclose`, jika keadaan bukan EXIT (sudah overlay) dan bukan sesi hilang → masuk round counter.
  Backoff: 500 ms, 1 s, 2 s, 4 s, cap 10 s.
- **Guard single socket**: sebelum membuka socket baru, paksa `ws.close()` yang lama; jangan pernah ada dua
  socket live (AFK-003).
- **AFK-004**: jika `/attach` mengembalikan 404 (SESSION_NOT_FOUND) atau frame EXIT diterima → **stop** loop,
  tampilkan `setDisconnectReason('Sesi diakhiri server')`, overlay permanen; jangan retry lagi.
- **AFK-007**: saat `reconnecting`, tampilkan `<span className="term-reconnect">• Menghubungkan ulang…</span>`
  di pojok terminal, bukan overlay penuh.
- Bersihkan `setTimeout`/socket di cleanup efek agar tidak leak (perlu `useRef` untuk timer/socket).

### Milestone B — Kehadiran tab & keepalive (AFK-005..006)

- Dengarkan `visibilitychange`: saat `visible` dan socket tidak live dan tidak sedang reconnecting → langsung
  panggil fungsi reconnect tanpa menunggu backoff. Saat `hidden` → batalkan timer backoff (tunda sampai
  visible) agar tidak banjir reconnect saat layar dimatikan.
- `pagehide`/`beforeunload` → `ws.close()` rapi dan batalkan reconnect.
- `onmessage` PING tetap PONG (tidak berubah) — menjaga keepalive saat tab aktif (client side).

### Milestone C — Retention sesi server (AFK-009..011)

- Naikkan default `session_idle_timeout` 60 → **120 s** di `src/config.rs:63-64` dan
  `SessionConfig::default` (`src/session.rs:55`) agar idle tab tidak langsung membunuh PTY. Default baru
  tetap memungkinkan `=0` (reap disabled). Tambahkan env `MUX_WEB_SESSION_IDLE_TIMEOUT` sebagai override.
- `session_busy_grace` (30 s) tetap.
- Verifikasi otomatis (test cargo): detach → sleep > `grace` kecil → reconnect → pastikan
  `attach_session` meng-clear `idle_deadline` sehingga sesi tidak direap (AFK-010).
- Pastikan `test_sess_009_no_orphan_children_after_shutdown` tetap hijau (AFK-011).
